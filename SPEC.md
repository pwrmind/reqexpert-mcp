## Этап 1. Анализ проблемной области и стейкхолдеров

**Экспертная роль:** бизнес-аналитик.

**Шаги и результаты:**
1. Выявлены стейкхолдеры: аналитик требований, product owner, системный архитектор, QA, технический писатель, compliance-офицер, интегратор СУТр, LLM-инженер.
2. Зафиксированы боли: ручное выявление требований, потеря трассировки, неоднозначные формулировки, разрозненные инструменты, долгий цикл согласования.
3. Определены границы: система не заменяет СУТр, а оркестрирует LLM-агентов и MCP-серверы, интегрируется с Devprom, Jama Connect, Polarion, DOORS, ReqView через API/ReqIF.
4. Конкурентный контекст: российские Devprom СУТр, Техэксперт СУТр, MIRaR, Platform V Works::Wiki; зарубежные Jama Connect, Visure Requirements, ReqView, Siemens Polarion, IBM Rational DOORS.

**Фиксация в ReqExpert:**  
`add_stakeholder` для 8 ролей; вовлеченность: высокая — аналитик, product owner, архитектор; средняя — QA, техписатель, интегратор; низкая — compliance.

## Этап 2. Бизнес-цели и пользовательские требования

**Экспертная роль:** Product Owner.

**Шаги:** сформулированы бизнес-цели, персоны, пользовательские сценарии; выполнена декомпозиция «цель → пользовательская потребность → измеримый результат».

| ID | Тип | Приоритет | Формулировка | Критерии приемки |
|---|---|---|---|---|
| REQ-001 | Бизнес-требование | Must | Сократить цикл выявления и документирования требований не менее чем на 40% за счет LLM-агентов и MCP-интеграций | Пилот на 3 проектах; среднее время от исходных материалов до черновика SRS снижено ≥40%; отчет зафиксирован |
| REQ-002 | Пользовательское | Must | Аналитик получает черновики требований из документов, встреч и тикетов с указанием источника и уверенности | Поддержано ≥3 типа источников; у каждого требования есть source и confidence; точность извлечения ≥80% на тестовом наборе |
| REQ-003 | Пользовательское | Must | Аналитик декомпозирует цель до FR/NFR с трассировкой | Для каждой цели строится дерево связей; покрытие целей требованиями 100%; трассировка экспортируется |
| REQ-004 | Пользовательское | Must | QA проверяет качество требований по правилам D25/D26/H78 | Проверка запускается при создании/обновлении; формируется отчет violations |
| REQ-005 | Пользовательское | Should | Технический писатель генерирует SRS в Markdown и экспортирует в ReqIF/Word | SRS содержит стейкхолдеров, требования, трассировку; экспорт сохраняет ID |

**ReqExpert:** `add_requirement` вернул `validationPassed: true` после корректировки критериев приемки; `qualityScore` — 90–100.

**Экспертная роль:** системный архитектор.

**Шаги:** определены компоненты: MCP-шлюз, оркестратор LLM-агентов, реестр агентов, хранилище project state, агенты выявления/анализа/декомпозиции/валидации/документирования, адаптеры СУТр. Данные передаются через MCP-ресурсы и tools; все вызовы валидируются Zod.

| FR-002 | Функциональное | Must | Реестр LLM-агентов с ролями, моделями, промптами, версиями, правами | CRUD агентов; назначение ролей; версионирование промптов; аудит изменений |

## Этап 4. Функциональные требования по подсистемам

**Экспертная роль:** ведущий инженер требований.

**Шаги:** детализированы подсистемы: ingestion, выявление, анализ, декомпозиция, валидация, документирование, трассировка, изменения, интеграция, коллаборация, поиск, администрирование, аудит, доступ, экспорт, отчеты.

| ID | Приоритет | Формулировка | Критерии приемки |
|---|---|---|---|
| FR-005 | Must | Ingestion источников: PDF, DOCX, MD, JSON, CSV, транскрипты встреч, тикеты | Загрузка ≥6 форматов; извлечение текста; сохранение source; ошибки парсинга логируются |
| FR-006 | Must | Агент выявления требований формирует кандидаты с title, description, source, confidence | Точность ≥80% на тестовом наборе; дубликаты не создаются без подтверждения; confidence указан |
| FR-007 | Must | Агент анализа классифицирует тип, приоритет MoSCoW, статус; выявляет конфликты и пробелы | Для каждого требования заполнены type/priority/status; отчет конфликтов; отчет пробелов |
| FR-008 | Must | Агент декомпозиции строит дерево «бизнес-цель → пользовательское → FR/NFR» | Для каждой цели есть дерево; предлагаются атомарные требования; проверка D25 запускается |
| FR-009 | Must | Агент валидации запускает D25/D26/H78 и формирует issues | При high strictness violations утверждение блокируется; повторная проверка после исправления |
| FR-010 | Must | Агент документирования генерирует Markdown SRS с разделами и трассировкой | SRS содержит стейкхолдеров, требования, трассировку; экспорт в ReqIF/Word; версия SRS |
| FR-011 | Must | Трассировка требований goal→user→FR→NFR→test | Матрица трассировки; покрытие 100%; экспорт матрицы; анализ влияния при изменении |
| FR-012 | Must | Управление изменениями с impact analysis | При изменении ID показываются dependents/relatedBySource/risk; для Must требуется approve; история версий |
| FR-013 | Should | Интеграция с внешними СУТр: Devprom, Jama, Polarion, DOORS, ReqView | Адаптеры через API/ReqIF; импорт/экспорт требований и связей; маппинг полей настраивается |
| FR-014 | Should | Коллаборативное ревью: комментарии, статусы, назначение ревьюеров, уведомления | Комментарии привязаны к требованию; статусы меняются по workflow; история ревью сохраняется |
| FR-015 | Should | Поиск по знаниям: полнотекстовый и семантический поиск требований/правил | Поиск ≤2 с; фильтры по типу/приоритету/статусу; семантический поиск по embedding |
| FR-016 | Must | Администрирование правил ЭС: добавление, версии, active, sandbox timeout | `add_expert_rule` работает; версии правил; timeout 100 мс; журнал изменений |
| FR-017 | Must | Аудит вызовов MCP и LLM-агентов | Логируются user, traceId, timestamp, tool, результат; хранение ≥90 дней |
| FR-018 | Must | Управление доступом: RBAC, API-ключи, секреты | Роли admin/analyst/qa/viewer; секреты не попадают в логи; ротация ключей |
| FR-019 | Should | Экспорт/импорт project state в JSON по схеме | Round-trip без потери ID; валидация Zod; ошибки импорта возвращаются结构化 |
| FR-020 | Should | Отчеты качества: покрытие, violations, риски, impact | Отчет по проекту; фильтры по периоду; экспорт PDF/Markdown |

**ReqExpert:** все FR добавлены; для FR-006 первоначальная формулировка содержала «быстро», `check_ambiguity` выявил D26, формулировка заменена на измеримую. После `update_requirement` — `validationPassed: true`.
